# observability — logs (Loki) and traces (Tempo) in Grafana

**Type:** knowledge + procedure (writes instrumentation code). Panels and alerts:
`/grafana-dashboards`.

```
app ──stdout JSON──► Promtail ──► Loki ──┐
 │                                        ├── Grafana (<grafana-host>, SSO)
 └──OTLP/http──► otel-collector ──► Tempo ┘      trace_id links a log to its trace
                 (DaemonSet, hostPort 4318)
```

Sources, more complete and dated — read them before claiming anything about an app:
- Logs per app: your team wiki's logging page (e.g. `Architecture/operations/logging.md`).
- Traces: your infrastructure repo's tracing doc (e.g. `docs/observability/tracing-tempo.md`).
- Reference implementation of both: your reference repo, e.g. a Rails app with
  `lib/grafana_log_formatter.rb`, `config/initializers/lograge.rb`, `lib/otel.rb`, and an `otelEnv`
  helper in `k8s/templates/_helpers.tpl`. Adapt to your stack.

## 1. Logs: one event = one JSON line

Free text (`Rails.logger.info "Starting import"`) cannot be aggregated with `| json`. Rules:

- One JSON line per event, stable `snake_case` keys and an `event` field (`<domain>_<past_tense_verb>`).
- Anything you will filter or aggregate on goes in a top-level key, not inside the message.
- Keys are an API: adding is free; renaming silently breaks panels and alerts.
- No secrets, tokens or `Authorization`; bodies truncated to ≤500 characters.
- Reuse a contract before inventing one:

| If you log… | Contract | Detail |
|---|---|---|
| a call to an external service | `http_outbound_request` / `_response` / `_error` | `references/http-outbound.md` |
| a job, importer or cron that loops over rows | `import_run_*` + `import_item_*` (`pipeline`, `run_id`) | `references/importer-events.md` |
| a fan-out to subscribers | `webhook_*` (by `owner`) | `references/webhook-fanout.md` |

**Check that the process emits JSON**, not just the app. Keep a per-app record of which apps do
(and of quirks such as a Python app putting the level in `levelname`, not `level`); a pure SPA
served by nginx typically has only the nginx access log. The trap: the worker is not the web
process. In one Django app, Celery (`worker_hijack_root_logger`) replaced the worker's logging and
its logs went out as plain text for weeks. Look at how the specific process you are instrumenting
configures logging.

## 2. Traces: OpenTelemetry → Tempo

Keep a record of which apps export traces today. To instrument another app, the contract (your
tracing doc):

1. Export OTLP to the **node's** collector: it has no Service. `OTEL_EXPORTER_OTLP_ENDPOINT=http://$(OTEL_NODE_IP):4318`
   with `OTEL_NODE_IP` from `status.hostIP`. A Service DNS name loses every trace with no error.
2. `OTEL_SERVICE_NAME` = the container name, or the trace-to-logs jump comes up empty.
3. `trace_id` (and `span_id`) on **every** log line, taken from the active span, not generated by the app.
4. Do not trace `/liveness`, `/readiness`, `/health_check`.
5. Configure via `OTEL_*` in the chart values (`otel.enabled`, `otel.samplerRatio`), not in code;
   without `OTEL_EXPORTER_OTLP_ENDPOINT` the app does not trace (that keeps dev and test untouched).

Limits (adapt to your setup): e.g. Tempo keeping **24 h**, one replica on local disk. Known Ruby
traps: Rails instrumentation that installs nothing, a frozen `untraced_endpoints`, and `aws_sdk`
instrumentation lengthening boot by ~44 s. Document yours in the tracing doc.

## 3. Reading logs — a Loki query tool

Use a Loki query tool / MCP if available (e.g. tools like `labels`, `count`, `query`, `stats`,
`tally`), or Grafana Explore otherwise.

- **The namespace carries app and environment, and is not always the app's own:** e.g. a backend
  API may log in a namespace named after a sibling app (`web-staging` instead of `api-staging`).
  A made-up namespace returns 0 lines, which looks like "there were no logs". When in doubt, list
  the values of the `namespace` label.
- **One app is several `service_name`s:** e.g. `api-worker` is the background jobs (Sidekiq).
  Use `service_name=~"api.*"`.
- **Always `| json | __error__=""`**: a non-JSON line aborts a bare `| json`.
- **"How many?" → an exact count** query. Sampled query/tally tools have a cap: their number is a minimum.

```
count  logql: '{namespace="<app>-staging", service_name=~"<app>.*"} | json | __error__="" | event="import_item_failed"'  by: ["pipeline"]  since: 24h
```

## 4. Reading traces — TraceQL in Grafana

Grafana → **Explore → Tempo → TraceQL** (unless you have a Tempo tool/MCP).

```traceql
{resource.service.name="<app>" && span.http.response.status_code>=500}
{resource.service.name="<app>" && span.url.path=~"/api/v1/.*" && duration>1s}
{span.import.run_id="<run_id>"}
```

From a Loki log, the `trace_id` opens the trace; from the trace, "Logs for this span" goes back to
Loki. In the browser, the response's `traceparent` header carries each request's `trace_id`. If
TraceQL returns nothing, check the time range first (retention).

## Before calling the instrumentation done

- [ ] JSON line, stable `event`, filterable top-level fields, no secrets.
- [ ] The specific process (web/worker) emits JSON.
- [ ] Deployed and **seen in Loki** with an exact count in staging; if there are traces, the trace shows up in Tempo.
